# Honeymoon cost connections

Run `supabase/travel-costs.sql` after shared-travel.sql and the installed retailer/shared-finance migrations. Downloadable copy: `C:/Users/ayeni/Downloads/cobridey-travel-costs.sql`. Existing travel plans, private records, expense agreements, payments and refunds are preserved. No provider setup or new key is required.

Open **Honeymoon Planning & Travel → Plan with partner → trip → Travel costs**. A confirmed/booked/completed activity can connect to an existing ledger expense or create one explicitly reviewed commitment. The trip creator must also have current financial and project editing access and confirm the fields shared with financial collaborators. Creation copies only the reviewed title, supplier, native currency, total and budget category. Reservation references, provider URLs and itinerary notes are not copied. The shared activity feed uses a generic expense action rather than private travel details.

Trip membership alone never grants financial access. Reading costs requires both current trip access and the wedding's financial permission. Other financial collaborators may see the deliberately shared canonical expense but do not gain access to the private trip. Financially restricted trip users receive an unavailable response with no expense records, IDs, currencies or totals.

A unique item/expense connection prevents duplicate counting. Exact request IDs handle interrupted retries; expected trip, activity, connection and expense revisions reject stale changes. Linking an existing expense creates no new financial obligation. A reviewed correction can choose another existing expense, preserving the previous agreement and its payment journal; it never silently cancels the old ledger record. Source edits flag a review without rewriting the amount. A confirmed review of the same current expense can refresh that source connection. Cancellation of travel also leaves financial obligations intact, so supplier cancellation terms and refunds are handled explicitly in the ledger.

The cost panel reads original ledger commitments (including reviewed settlements), payments and refunds. Net payments and balances remain signed, and currencies are grouped separately without adding unlike amounts or converting them. Payment creation, refunds, installments, receipt access and reconciliation stay in their existing permission-controlled ledger workflows. Creating a cost does not move money, book travel or imply a payment. Existing private honeymoon budget records remain independent; this step creates no second payment journal.

Tests use the actual retail expense, shared ledger, payment/refund and settlement functions. Coverage includes duplicate retries, stale sources, source reconfirmation, selected trip users without financial access, financial users without trip access, original-currency grouping, existing-obligation links, correction without journal deletion, cross-wedding rejection, cancellation without inferred refunds, and mobile review controls. UI tests also check that refreshing cost data does not advance the parent itinerary revision and permit stale overwrites. Live account/device testing remains deferred by the user.
