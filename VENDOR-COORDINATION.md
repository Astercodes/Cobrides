# Shared vendor coordination

Apply `supabase/vendor-coordination.sql` after shared-vendors.sql and collaboration-access.sql. It is repeatable, RLS-protected, and does not publish personal vendor boards or commercial terms. Open Vendors & venues → Team directory → a professional → Coordination. The private vendor coordination page also has a Shared vendor coordination entry leading to the team directory. Invited collaborators use Team vendors in their shared workspace.

Planning writers can create/review deliverables, setup windows, rehearsals, logistics and issues, with an optional accepted assignee who can already access that vendor. Financial access is not required. An assigned non-manager sees only their own work for that vendor, can update progress, and cannot rewrite instructions or reassign the work. No new access is inferred from an assignment. Reassignment or loss of vendor/project access revokes visibility and updates immediately.

Statuses: To do, In progress, Blocked, Ready, Complete; planning writers may also cancel work. Blocked/completed work requires a note, and cancelled work requires a note in the manager editor. Non-managers cannot reopen completed/cancelled work. Vendor/project archival disables mutations. Project locks, optimistic revisions and exact-request UUID journals protect conflicting edits and uncertain retries. Snapshots retain each work version; visible history includes operational progress metadata only. Generic activity messages omit commercial terms and work-note content.

The dialog refreshes visible idle boards every twenty seconds and offers manual Refresh. An in-flight refresh does not overwrite an editor opened while it was loading. These are operational planning records, not live vendor location tracking, automated external dispatch or hardware control. No email/messages are sent by installing the migration. Existing task-board and financial permissions remain separate.

SQL/mobile tests cover planners without finance access, selected vendors, assignment isolation, progress validation, retry idempotency, version conflicts, reassignment and mobile form behavior. Live account testing remains deferred at the user's request.

## File submissions and review

Apply `supabase/vendor-deliverables.sql` after vendor-coordination.sql and the existing file-storage/recovery setup. Open a coordination item → Files & approvals. Assigned vendors and planning writers can submit an owned, verified file; planning writers can approve or request changes on the latest pending version. Feedback is required for requested changes. Review decisions are final per version; a revision is another immutable upload, and a newer upload supersedes pending older versions. Work-instruction revision checks protect submissions against a changed brief; exact client request journals make interrupted retries safe. File approval does not automatically complete the coordination item or mark payments made.

Files live in the separate private `cb-vendor-deliverables` bucket. PDF, JPEG, PNG, WebP, text, CSV, DOCX and XLSX are accepted, up to 20 MB per file, within the existing 500 MB account allowance. The migration extends installed quota/cleanup functions rather than resetting storage migrations. Each work item supports fifty submission versions. All referenced versions remain protected from unused-file cleanup. Financial files remain in their own bucket and cannot be attached through this submission endpoint.

Storage access is limited to the uploader's own object or a user currently authorized for the work item. Reassignment and revoked project/vendor access block new shared downloads. Already issued sixty-second shared download URLs and previously downloaded copies cannot be recalled; uploader ownership remains in effect. Downloads recheck access, validate the storage origin and do not embed active document content. There is no public URL or automatic external email dispatch.

SQL/mobile tests cover ownership, dedicated storage policies, actual quota-function extension, file-size/allowance limits, idempotent submissions, feedback, immutable decisions, superseded versions and reassignment. Apply migrations in order; if older storage/reference migrations are rerun, reapply this deliverables migration afterward to retain its latest cleanup integration.
