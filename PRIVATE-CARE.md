# Private care check-ins

Run supabase/private-care.sql after record-based workspace saving is installed. Existing beauty appointments, routine definitions, products, costs and older check-in history remain in the owner's normal workspace records. This migration adds independently versioned daily routine steps/completion/undo and private correction history. It does not share care data with wedding collaborators, book providers, send messages or record payments.

The existing routine controls now save through authenticated RPCs. The server reads the current routine definition from the account's saved preparationRecords (including separated personal/demo envelopes), validates its project, kind, active status, steps and start date, then checks the expected day revision. Future check-ins, duplicate/unknown steps, incomplete completions and stale writes are rejected. It locks the workspace head against concurrent definition changes. Routine definitions are committed before a daily write, and independent check-in records are hydrated back into the current preparation views and owner workspace cache. Existing older check-ins remain intact. The view reads the past 91 days of native daily records; new actions use the user's current local date and validated timezone.

Daily records and history have no direct client/table grants. RPCs always use auth.uid(), never a supplied user ID or collaborator role. Personal and demonstration records are distinct. Exact request IDs protect retries, and changing account/project prevents old responses from updating the new UI. A write that cannot reach the server is shown as an error without claiming success. Offline queuing of new care actions is not introduced here; the existing workspace outbox continues protecting other saved edits.

Tests: private-care.sql.test.cjs (ownership, raw-table denial, scoped data, dates, steps, completion/undo, retries and conflicts); private-care.ui.test.cjs (existing controls, definition commit, day revisions, completion/undo). Real-account multi-device testing remains deferred at the user's request.
